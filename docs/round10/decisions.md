# Round 10 decisions

- **track-d merged without its d5 review.** The owner asked for the merge and a release at once. The partial d5 run (keyframes 81f6f353, withers d4f932de..ef9ad9de, wind charges f142f9c1) stopped before its review. Track D's round 10 review uses base `r9-d5-base`, so it covers those commits too.
- **The relay needs no rebuild for protocol 6.** `iw4l-master` carries Minecraft messages as opaque packets and does not depend on `minecraft_net`. Its own protocol is `master_protocol::PROTOCOL_VERSION` 10, unchanged since e06114b0 (2026-10-11). The `iw4l-master.exe` in the game folder has the same SHA-256 as `D:\iw4l-target\release\iw4l-master.exe` from release 2. Its file date is 13 October because cargo did not relink an unchanged binary. Every release still builds it with `-p iw4l-master` and copies it in.
- **Five tracks at a time, set by disk.** D: had 27 GB free and C: 19 GB. A track's target dir is 6-8 GB, and 12-14 GB after a full suite. So at most five track target dirs exist at once, four on D: and one on `C:\iw4l-wt\`. Test binaries are deleted from a target after its merge's full suite. The two cargo slots are shared by all of them.
- **Phantoms go to the M3 mob track, not track E.** A phantom is a new mob family, so it uses D0's shared mob registry like the other remaining mobs. Track E keeps the other known limits.
- **PROTOCOL is bumped only at release time.** Tracks run in parallel and must not bump `minecraft_net::PROTOCOL` (several bumps would collide at merge, and some briefs say "bump to 7"; the run notes override that). A track that changes a message notes it under "## Protocol" in its log. Before a release build, if any merged commit since the last release changed a message, one commit bumps PROTOCOL by one (with its codec test asserts).
- **Tracks run in segments.** Each track-runner run is a few groups with its own review, so finished segments can merge for the daily releases and a stopped session loses at most one segment. Every run's args are saved in `docs/round10/runs/<segment>.json` before it starts (round 9 lost its launcher scripts with the session scratchpad).
- **Track D's first segment reviews round 9's d5 work.** Its review base is `r9-d5-base`, so the review also covers keyframes, withers and wind charges.
- **D0's shape: a static mob-family registry.** A new family is its own files plus one line in its track's own group file (entities, spawn rows, terrain). Each group owns a range of hit-key bytes so parallel tracks never collide: pests (D0) 36-39, trial (D) 40-43, deep_dark (W) 44-47, land (M1) 48-63, water (M2) 64-79, night (M3) 80-95, bosses (F) 96-99. D0 adds one generic arm at every shared site, and the tracks never edit those sites again. Existing families keep their code. Friends get a generic `MobShow.family` payload (flags and eight values). Silverfish and endermites are the proof family. The horse family (camels, camel husks, zombie and skeleton horses) stays in the cow store and goes to M3, the only track allowed to edit the old kind lists for it.
- **The mob split differs from round 9's batches.** Camels and camel husks moved to M3 (they share the cow store's horse kinds with the undead horses). Bees and sniffers moved to M1. The sulfur cube moved to M2 (it is bucketable). Silverfish and endermites moved to D0 as its proof.
- **First Elden Ring boss: Margit, the Fell Omen** (track F's design doc, `docs/ELDEN-RING-BOSSES.md`). He is humanoid, has two phases and a readable moveset, and fits an altar summon. His numbers are marked as estimates until real game data exists. He is saved as a `minecraft:marker` carrying fork data, which vanilla keeps and ignores, and loading resets the fight.
- **Elden Ring is not installed on this PC** (no Steam install on C: or D:). Track F's proof of concept cannot read game files. It uses a stand-in model and our own data. `docs/ELDEN-RING-BOSSES.md` says what real game data would need later.
